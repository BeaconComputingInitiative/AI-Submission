# BEACON COMPUTING INITIATIVE
**Developer Seal:** `CJB-DEV-2026`  
**Component:** A440 M2.16.2 — System-wide concurrent evidence and reasoning architecture  
**State:** Design and isolated prototyping; deployment and complete integration **not yet verified**  
**Policy:** Research-only, explicit authorization, default-deny promotion

## Objective

Allow A440 to **interpret newly arriving authorized evidence while continuing inference on an immutable verified snapshot**, without corrupting provenance, reading partially committed state, or changing active model weights during a request.

The goal is reduced blocking and sustained availability, **not** a claim of greater predictive accuracy or autonomous reasoning skill.

## Execution lanes

| Lane | Execution model | Owns | Forbidden operations |
| --- | --- | --- | --- |
| Authorized acquisition | `asyncio` for network/file I/O with bounded concurrency | Explicitly approved sources, pull cursors and retry metadata | Untargeted scanning, secret extraction |
| Semantic interpreter | Bounded `multiprocessing` worker pool | Format discovery, data typing, dimensional/temporal interpretation and quarantine | Mutating verified snapshots; guessing unknown units |
| Condenser + ledger | Single-writer SQLite WAL coordinator | Source/version hashes, dedup keys, records, quarantine ledger, atomic snapshot commit | Serving uncommitted observations |
| Inference | Isolated process with pinned model/checkpoint SHA | Read-only reference to a committed evidence snapshot; result citations | Loading modified model weights mid-request |
| Conductor | Independent low-priority process | Candidate research training, independent validation and SHA manifests | Direct replacement of active weights; retraining from unauthorized data |
| Supervisor | Main process | Health monitoring, bounded queues, timeouts, restarts and clean shutdown | Reporting a HOLD as a successful promotion |

Use OS processes for CPU-heavy work where isolation matters. Limit PyTorch/BLAS intra-op threads per process to prevent CPU oversubscription. Start conservatively on resource-limited hosts (one interpreter, one inference process, one single-writer coordinator); scale only after benchmarking.

## Consistency and safety contract

1. A source observation becomes **eligible** if and only if source authorization, current source hash, semantic mapping, units, temporal interpretation and provenance pass verification.
2. An evidence version becomes **visible** to inference if and only if the single writer has committed the entire transaction and its content hash, semantic contract version, logical snapshot sequence and source lineage.
3. A reasoning request pins one `snapshot_id`, `compiler_sha256`, `model_sha256` and `source_contract_sha256` for its full execution. The supervisor MUST NOT substitute a later snapshot mid-request.
4. Changes to schema, units, aggregation, or reporting period create a **new typed contract version**. Ambiguous changes are quarantined rather than silently recast.
5. Candidate model weights become available for optional promotion if and only if independently evaluated, provenance-verified, policy-authorized and atomically installed with rollback metadata. **All M2.14–M2.16 candidates remain research-only.**
6. On queue overload, apply backpressure, bounded retries and a durable dead-letter queue rather than uncontrolled memory growth or silent data loss.

## Minimum durable record

```text
event_id / source_id / source_sha256
source_contract_sha256 / compiler_sha256 / semantic_type / unit
event_time / observed_at / received_at / reporting_period
original_payload_sha256 / normalized_payload_sha256 / coverage
quality_flags / quarantine_reason / ledger_sequence / snapshot_id
model_sha256 / prediction_as_of / outcome_verification_status
```

Preserve the difference between event timestamps and reporting periods. A monthly unemployment rate is a rate associated with a reporting interval, **not** a daily additive measurement; earthquake magnitudes are logarithmic events, not an arithmetic daily sum.

## Worker protocol and state transitions

```text
AUTHORIZED_SOURCE
  -> FETCHED -> PROFILED -> SEMANTICALLY_QUALIFIED
  -> COMMITTED_TO_LEDGER -> SNAPSHOT_SEALED
  -> INFERENCE_READY (read-only)
  -> ELIGIBLE_OUTCOME (only when independently verified)
  -> CANDIDATE_TRAINING -> EVALUATION
  -> HOLD | RESEARCH_ACCEPTED
```

All actions must be idempotent by content-derived identifiers and exactly-once **logical commit**; OS queues and remote fetches may be at-least-once. A failed worker must never count as an accepted observation.

## Required acceptance tests before saying "system-wide applied"

- Tests for duplicated, reordered and dropped messages, interrupted commit and restart recovery.
- Replayed source record produces no duplicate ledger insertion.
- Inference remains pinned to snapshot N while interpretation commits N+1.
- Unauthorized/ambiguous sources are quarantined; protected data never crosses into a training worker.
- Queue saturation triggers explicit backpressure, bounded memory and observable HOLD.
- A crashed worker cannot create a partial snapshot or silently lose unacknowledged work.
- Concurrent reads and ledger writes preserve hash-chain verifiability.
- Trainer cannot change serving model SHA during inference; rejected candidate leaves previous checkpoint untouched.
- Verified compiler input parity across offline training and live inference on all qualified data types.
- Measured worker latency, CPU/memory pressure, and output correctness versus sequential execution.

## Current limitations

The existing M2.15.2 128-input compiler supports the three previously enrolled daily-additive research domains. The four additional source types from M2.16.1.1 have **not** been qualified for neural training. Adding concurrency must not bypass that semantic HOLD.

This document specifies the intended concurrency system. GitHub publication of this design does not itself install or run concurrent workers on the user's Kali workstation.
